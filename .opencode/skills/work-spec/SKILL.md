# Work Spec

Run the spec as the **main orchestrator**. Keep dependency decisions, model
routing, worker lifecycle, and final verification in the calling agent; delegate
ticket implementation to fresh OpenCode agents in Herdr tabs.

## 1. Establish The Spec

Load the `herdr` and `ticket-model-routing` skills. Follow their current
instructions rather than relying on remembered CLI or model details.

Read the complete spec or parent issue, its comments, linked decisions, child
tickets, acceptance criteria, and native blocking relationships. If executable
tickets do not exist, load `to-tickets` and complete its approval and publishing
flow before continuing.

This step is complete when every executable ticket and blocking edge is known,
or the missing information is reported as a blocker.

## 2. Claim The Orchestrator Tab

Verify the caller is inside Herdr before issuing control commands. Rename the
current tab to `<spec reference> <short title> | main orchestrator` and rename
the current pane `main orchestrator`. Keep focus in this tab.

Use the current workspace and repository directory for every worker. Create a
new tab, not a pane or worktree, for each ticket. Preserve the caller's working
directory and use `--no-focus` for worker tabs.

This step is complete when the current tab and pane visibly identify the spec
and main orchestrator role.

## 3. Route The Whole Graph

Run `ticket-model-routing` against the complete ticket set before starting
implementation. Record each ticket's model, effort, confidence, and escalation
condition. Treat the routing result as immutable for the run unless its stated
escalation condition occurs.

Start each worker as an OpenCode agent with its assigned model. Prefix canonical
OpenAI model IDs with `openai/` when passing them to OpenCode. Put the routed
effort in the worker prompt. Never substitute a model silently; report an
unavailable model and wait for a routing decision.

This step is complete when every ticket has exactly one model and effort
assignment.

## 4. Work The Frontier

The **frontier** is every open ticket whose blockers are closed. Recompute it
after every ticket changes state.

Look for parallel opportunity whenever the frontier has multiple tickets:

- Create one labeled Herdr tab per frontier ticket and start its routed
  OpenCode agent.
- Run read-only preflight concurrently when useful. Each worker reports its
  expected write set, shared integration files, generated artifacts, focused
  tests, and any hidden blocker without editing the worktree.
- Treat package manifests, lockfiles, generated files, shared configuration,
  migrations, and overlapping tests as integration hotspots.
- Keep the shared worktree single-writer for implementation, verification,
  staging, and commits. Parallel mutations make one worker observe another's
  uncommitted state and make verification ambiguous. True parallel writes
  require separate worktrees and are outside this skill.

Choose the next writer from the frontier after preflight. Prefer the ticket
that unlocks the most downstream work; break ties by lower integration risk.
Never start a blocked ticket.

This step is complete when one frontier worker owns the write phase and every
other worker remains read-only or idle.

## 5. Dispatch One Ticket

Before prompting the writer, capture the current branch, HEAD, and
`git status --short` as the handoff baseline. Prompt the worker to:

1. Read the full ticket, comments, repository instructions, and linked domain
   decisions.
2. Confirm every blocker is closed.
3. Implement only that ticket in the existing worktree.
4. Preserve baseline changes and stage only paths owned by the ticket.
5. Run focused tests and all repository-required quality gates.
6. Remove artifacts generated by its own verification so the remaining
   worktree matches the handoff baseline.
7. Commit with the repository's commit convention, push, and close the ticket
   only after verification succeeds.
8. Report the commit SHA, test commands and results, push status, issue state,
   and final worktree status. Stop with a precise blocker instead of beginning
   another ticket.

Wait for the worker to settle. If Herdr reports `blocked`, `unknown`, or a
failed wait, inspect the worker state and transcript before responding. Resume
the same ticket session for corrections; a fresh tab is for a fresh ticket.

This step is complete only when the worker supplies every requested result or
a concrete blocker.

## 6. Verify The Handoff

Verify independently from the main orchestrator tab:

- The intended commit exists on the expected branch and remote.
- The ticket is closed as completed.
- Its acceptance checks passed.
- The worktree matches the captured baseline apart from changes explicitly
  approved during the ticket.
- No generated or unstaged leftovers from the worker remain.

Send the worker back to clean or repair its own changes when a check fails.
Keep downstream tickets blocked until all checks pass. Once verified, mark the
worker tab done, recompute the frontier, and repeat from step 4 with a fresh tab
and the routed model for the next ticket.

This step is complete when the ticket is a verified closed node in the graph.

## 7. Close The Run

After every ticket is verified, run the spec-level integration checks and
compare the delivered graph with the parent acceptance criteria. Preserve the
parent issue unless its explicit workflow requires the orchestrator to close or
modify it.

Report:

- Tickets, models, efforts, tabs, commits, and final states.
- Parallel preflight used and serialization decisions made.
- Integration checks and results.
- Any unmet parent criterion or residual risk.

The run is complete when every ticket is accounted for, the integration checks
pass, and the shared worktree has returned to its initial baseline.
